# 技術選定理由

本ドキュメントでは、AI PFC Menu Generator 開発における主要な技術選定の理由と背景をまとめます。（※ドラフト版です。必要に応じて推敲してください。）

## 1. フロントエンド・フレームワーク

### Next.js (App Router) & React
* **選定理由**:
  * **SSR / RSC によるパフォーマンス**: 初期読み込み速度の向上とSEO（必要に応じて）に有利。
  * **API Routes の統合**: バックエンド (BFF層) の構築が同一プロジェクト内で完結し、Gemini APIの呼び出しやレート制限の実装が容易。
  * **Vercel エコシステムとの親和性**: デプロイが簡単で、Edge Functions や Middleware の活用がスムーズに行える。

## 2. スタイリング・UI

### Tailwind CSS v4
* **選定理由**:
  * **開発スピード**: ユーティリティクラスを用いることで、CSSファイルとコンポーネントを行き来する手間を省き、高速にスタイリングが可能。
  * **レスポンシブデザイン**: スマートフォン向けのUI構築（モバイルファースト）が容易。
  * **一貫性**: デザインシステム（色、余白など）の統一がしやすく、メンテナンス性が高い。

### Lucide React
* **選定理由**:
  * 軽量でデザインの一貫性が取れたアイコンセットであり、Reactコンポーネントとして非常に扱いやすいため。

## 3. バックエンド・AI連携

### Google Gemini API (Gemini 2.0 Flash)
* **選定理由**:
  * **コストパフォーマンス**: 非常に安価（あるいは無料枠）で高速な応答が可能であり、個人開発のツールとして最適な選択肢。
  * **Structured Outputsの強力なサポート**: `responseSchema` を指定することで、確実に安定したJSON出力を得ることができ、フロントエンドでのパースエラーを防げる。
  * **推論能力**: PFCバランスの計算や、除外食材の考慮など、複雑な条件を満たす献立生成において十分な精度を発揮する。

## 4. 認証・データベース (BaaS)

### Supabase
* **選定理由**:
  * **Next.js (App Router) との親和性**: `@supabase/ssr` を使った Cookie ベースのセッション管理が公式で手厚くサポートされている。
  * **PostgreSQL ベース**: 将来的なマスタデータ（食材データ、ユーザーごとの履歴など）の拡張に柔軟に対応できる、強力なリレーショナルデータベース。
  * **学習コストと運用コスト**: Firebaseなどと比較してSQLの知識がそのまま活かせ、認証からDB管理までオールインワンで揃うため。

## 5. セキュリティ・インフラ

### Upstash Redis & Rate Limit
* **選定理由**:
  * **APIの保護**: 悪意のあるユーザーや想定外の連続リクエストによるGemini APIの過剰な利用（および課金）を防ぐため。
  * **サーバーレス互換**: Next.jsのEdge MiddlewareやServerless Functionsから非常に低遅延でアクセスでき、セットアップも容易なため。

## 6. フォーム管理・バリデーション

### Zod
* **選定理由**:
  * **型安全性の確保**: TypeScriptとの連携が強力で、定義したバリデーションスキーマから直接型を推論できる。
  * **フルスタックでの共有**: フロントエンド（フォーム入力）とバックエンド（APIリクエストボディ）のバリデーションロジックを共通化でき、二重管理を防げる保守性の高さ。

## 7. テスト

### Vitest & React Testing Library
* **選定理由**:
  * **Vitest**: Viteベースで非常に高速に動作し、Jest互換のAPIを持つため移行や記述が容易。TypeScriptとの統合もNext.js環境下でスムーズに構築できる。
  * **React Testing Library**: ユーザーの操作（振る舞い）に近い形でコンポーネントのテストが書けるため、実装の詳細に依存しない、リファクタリングに強いテストを作成できる。
