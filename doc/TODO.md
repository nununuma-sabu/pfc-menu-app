## アーキテクチャ・スケーラビリティの課題（将来的な設計見直し）
- [ ] **Supabase AuthのSPOF回避と高速化**
  - 現状: APIで毎回 `supabase.auth.getUser()` を呼び出しており、外部通信のレイテンシと単一障害点（SPOF）のリスクがある。
  - 対策: JWTシークレットを用い、自社サーバー（エッジ等）でローカルに署名検証を行う方式への移行を検討する。
- [ ] **トークンログの確実な保存（データロス対策）**
  - 現状: APIレスポンスを優先しDB書き込みエラーを無視しているため、DB障害時に重要な課金データ（トークン使用量）を失う。
  - 対策: メッセージキュー（SQSやRedisストリームなど）に一旦保存し、非同期ワーカーで確実にDBへ書き込む「結果整合性」の仕組みを導入する。
- [ ] **APIハンドラの関心事の分離（Cross-Cutting Concerns）**
  - 現状: `route.ts` に認証、レートリミット、バリデーションが直書きされており、API増加時にコード重複やテストの複雑化（モック地獄）を招く。
  - 対策: Higher-Order Function（高階関数）やカスタムデコレーターを導入し、ビジネスロジックと共通処理を分離する。
- [ ] **Vercelタイムアウト回避と重たい処理（LLM＋DBマスタ照合）の非同期化**
  - 現状: 同期的なHTTPリクエストでLLM生成と重たいDBマスタ照合を直列実行すると、Vercelのタイムアウト制限（10〜60秒）の壁に阻まれる（サーバーレス特有のスケーラビリティの壁）。
  - 対策（将来的に以下のいずれかの戦略で非同期アーキテクチャへ移行）:
    - **戦略1: ポーリングアーキテクチャ（Next.js単体・バッチ処理）**
      - API（route.ts）は即座に「タスク受付完了（202 Accepted）」とタスクIDを返す。
      - 裏側でUpstash QStashやVercel Cron等を利用し、非同期バッチとしてLLM生成・マスタ補正を実行。
      - フロントエンドは数秒おきにタスクステータスをポーリング（定期問い合わせ）する。
    - **戦略2: Edge Functions ＋ ストリーミングの活用**
      - Vercel Edge Functions等を使用し、コールドスタートの高速化とタイムアウト制限回避を図る。
      - Gemini APIのストリーミング（`generateContentStream`）を活用。データが1行（1食材）返るたびにフロントへ順次返しつつ、バックグラウンドで並行してマスタ照合を行う。
